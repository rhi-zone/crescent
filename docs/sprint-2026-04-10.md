## Architectural decisions

### Capability pattern
All platform capabilities are **plain tables** returned by factory functions (`png_cap`,
`llm_cap`, `render_cap`, `fs_cap`). The sandbox receives them via `{globals={...}}` wrapped
tables passed to `sandbox.env()`. No special capability type — just Lua tables, which means:
- Capabilities are composable without a framework
- Scripts can inspect capability shape at runtime
- The platform can wrap/proxy any capability trivially

### Script/data separation in cards
A card (PNG file) has separate `script` and `data` tEXt chunks. The platform loads the
script chunk and runs it. The editor writes the data chunk. The script reads its own data
via `caps.png.text("data")`. This means:
- Editors never modify script text → diffs stay clean
- The same script can run against different data (multi-character scenarios)
- No writeback into script source anywhere in the platform

### Entity-component store
`lib/ecs` is a minimal SQLite-backed ECS: entities have integer IDs, components are
named JSON blobs. No archetypes, no systems. The design is intentionally smaller than a
full ECS — derive shape from real consumers (RP scripts, Lumen) before adding complexity.

The `ON DELETE CASCADE` pattern (destroy entity → auto-removes all components) requires
`PRAGMA foreign_keys = ON` per connection. This is set in `store:init()`, which `ecs.new`
calls automatically.

### Signal/optics composability
`lib/reactive` and `lib/reactive_optics` are peers of Rainbow (the TypeScript
implementation). Neither depends on the other; both implement the same algebra. `lib/lua2ts`
is the bridge: write reactive UI in Lua, emit typed TS, run in browser with Rainbow.

### JSON-RPC transport abstraction
`lib/jsonrpc` takes a **transport object** (`{read(), write()}`) rather than assuming
stdio. This means:
- LSP daemon uses `stdio_transport()`
- Tests use `table_transport()` (in-memory)
- Future: TCP transport is just another transport implementation

### Render surface abstraction
`caps.render` takes a **session object** (`{push(), flush()}`) rather than assuming SSE
or WebSocket. Built-in sessions: `sse_session(write_fn)` and `collect_session()` (for
tests). This means the same card script works with a streaming HTTP response, a WebSocket,
or a test buffer.

## Consistency concerns

### Typechecker coverage gaps
All new libraries have some typechecker warnings or compromises:

- **lib/ecs** — all metatable method annotations removed; typechecker doesn't unify
  `setmetatable` return types with declared struct types. Same issue in lib/jsonrpc (9 warnings
  for `any` on `self`).
- **lib/log** — found a typechecker bug: `any?` as last parameter corrupts struct field
  resolution in the function body. Tracked in TODO.md. Workaround: use `any` (no `?`).
- **lib/platform/init.lua** — FIXME comment: typechecker doesn't narrow `card` from nil
  after `if not card then return end` in function-call argument position. Worked around by
  inlining `run_card` logic.
- **lib/tui** — 13 warnings for `any` on widget parameters (duck-typed by design).

The root issue: the typechecker's struct type declaration (`--::`) creates a closed table
type, but `setmetatable`-based objects don't unify with it. The typechecker doesn't have
a first-class "class" or "interface" concept for this pattern. This should be tracked as a
typechecker feature gap, not just worked around per-library.

### io.popen in lib/platform/caps/fs.lua
`cap.list()` uses `io.popen("ls -1 ...")` — Linux/macOS only, no Windows support.
Tracked as TODO. The fix requires native `readdir` via FFI (part of a future `lib/fs`
or `lib/socket` rewrite).

### lib/tui widget protocol
Widgets are duck-typed tables with a `render` method. The tui library supports both
`widget.render(ctx)` and `widget:render(ctx)` via an `unpack_ctx` helper. This is
pragmatic but means there's no formal interface. If `lib/lua2ts` emits this as TypeScript,
it'll need an interface or generic type.

### lib/log vs lib/reactive sinks
`lib/log`'s sink pattern (array of `sink(entry)` callbacks) is structurally similar to
`lib/reactive`'s effect system. They're not unified — log sinks are plain callbacks, not
reactive effects. This is fine for now, but worth noting: a reactive log sink would allow
live log level changes to propagate automatically. Not needed now; derive from real use.

### lib/sandbox instruction budget
The `opts.budget` instruction limit uses `debug.sethook`, which is not preemptive —
a C call (like an FFI operation) won't be interrupted. Scripts granted FFI access can
bypass the budget. The current sandbox is appropriate for trusted or lightly-trusted
scripts; untrusted scripts should not get FFI access regardless.

### lib/ecs vs caps.db
The platform hands scripts a `caps.db` capability for direct SQLite access. `lib/ecs`
wraps a sqlite connection. There's currently no `caps.ecs` factory in `lib/platform/caps/`.
Scripts that want entity-component semantics must wire it up manually:

```lua
local ecs = require("lib.ecs")  -- requires sandbox to grant this module
local store = ecs.new(db)       -- db from caps.db
```

This is intentional (platform doesn't hardcode world state model), but it should be
documented in `docs/platform-design.md`. A future `caps.ecs` convenience factory would
be trivial to add.

## Open questions

1. **zTXt chunks** — `lib/png` only handles `tEXt` (uncompressed). Self-contained cards
   embed editor scripts as `zTXt` (compressed). This requires `lib/compress` (zlib) before
   the full card embedding vision is implementable. Currently `lib/platform` only reads
   `tEXt` chunks named "script".

2. **caps.render + lib/reactive** — should `render_cap` integrate with signals? E.g.,
   a reactive render that re-renders when a signal changes. This would tie `lib/reactive`
   into the platform render loop. Not designed yet.

3. **lib/lua2ts output format** — does lua2ts emit ES modules (`import`/`export`) or
   CommonJS (`require`)? Does it emit `.d.ts` type definition files separately? The target
   is Rainbow, which uses ES modules. Answer: ESM is the right default.

4. **lib/hast and lib/mdast coupling** — lib/hast depends on lib/mdast's node type
   names. If mdast node names change (e.g., `softBreak` → `soft_break`), hast breaks.
   Should there be a stable mdast node type spec document?

5. **Entity IDs** — `lib/ecs` uses SQLite `AUTOINCREMENT` integer IDs. `lib/uuid` now
   exists. Should entities optionally support UUID primary keys for distributed scenarios?
   Not needed now; single-machine for all current use cases.

## Risk: over-optimization for the card platform

The crescent principle is *vendorable, hackable, composable, no hardcoded assumptions*.
Every library in this sprint was spec'd to serve the card platform. The risk is that the
interfaces quietly encode that application's shape even where they claim to be general.

**Places to scrutinize in the review:**

### lib/ecs — JSON-blob storage
The `ecs_components` schema stores all component values as JSON text blobs. This is
convenient for the card platform's loose, schema-free world state, but it's a poor fit
for anything needing typed columns, efficient range queries, or high-throughput writes
(e.g. a game engine's position components). A truly general entity store would probably
let the caller define the component schema. The question to ask: is `lib/ecs` a
general-purpose ECS, or is it specifically a card-platform component store that happens
to be extracted into a library?

### lib/tui — render model assumptions
The absolute-position render model (widgets produce escape sequences at specific screen
coordinates) follows terminal dashboard conventions. It's a reasonable choice but an
opinionated one. `lib/ansi` is the truly general primitive here; `lib/tui`'s widget/layout
model imposes a specific mental model of TUI construction. Worth checking: does the widget
protocol (duck-typed `render(ctx)` tables) leave room for other TUI paradigms (e.g.
immediate-mode, retained-mode with diffing), or does it commit to one?

### lib/platform/caps/render — SSE orientation
The built-in sessions are `sse_session` (Server-Sent Events over HTTP) and
`collect_session` (test buffer). SSE is the right choice for the card platform's web UI,
but it's a web-specific transport. A terminal-mode card runner would need a different
render surface. The `render_cap(session)` factory is technically transport-agnostic — any
object with `push/flush` works — but the library signals SSE as the primary use case.
Worth checking: is it obvious enough that callers can plug in any session, or does the
API nudge toward web?

### lib/reactive — Rainbow-shaped
`lib/reactive` is modeled directly on Rainbow (the TypeScript implementation). Rainbow is
a good design, but it was built for browser component trees. The push-based,
explicit-dependency-array model may impose a browser-component mental model on use cases
that don't need it. Worth asking: would a Lua developer reaching for reactive primitives
for, say, a data pipeline or a game loop naturally reach for this API, or does it feel
like a port?

### The meta-question
The right test for each library: *if the card platform had never been conceived, would
this library look the same?* If yes, it's genuinely general. If no, the card platform's
shape has leaked into the design and the library will resist reuse in other contexts.
