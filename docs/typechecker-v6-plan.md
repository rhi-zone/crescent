# Typechecker v6 Design

Status: v6 is prototype/research input. If work targets the current
type-system-agnostic framework direction, use `docs/typechecker-framework.md`
as authority. Any v6 rule must be restated as a theory rule with framework
evidence obligations before it is implementation guidance for new architecture
work.

v4 is the running checker. v5 is research material. v6 is a new line: derive
the full checker from the Lua value universe and the ways values move through
programs, then implement it as thin vertical slices that integrate into one
coherent semantics.

This is not the 19-axis plan. "Question-first" is a derivation discipline, not
an architecture boundary. Features do interact. The point is to admit a feature
only when its interaction with the whole checker is explicit, tested, and
legible.

## Status

This document is the v6 pinning target. The core verticals are implementable
from this spec; reserved extensions remain explicitly outside core. Its job is
to make the checker shape falsifiable:

- if a rule follows from value sets + movement sites, keep deriving it;
- if a rule needs a new primitive, name the primitive and justify it;
- if a rule needs a name-keyed handler, treat that as a design failure;
- if an interaction is unclear, mark it open before writing code.

## Core Derivation

A type is a claim about the set of runtime values an expression may produce.

Checking asks one question at every movement site:

> Can every value the producer may produce be safely consumed here?

All v6 features must reduce to this producer/consumer question. Features that do
not reduce to it are not core.

The checker therefore has four semantic layers:

1. **Value algebra** — the language of claims about runtime values.
2. **Movement sites** — syntax locations where claims are consumed or
   transformed.
3. **Proof obligations** — checks generated by annotations, calls, returns,
   writes, guards, overloads, modules, and casts.
4. **Facts** — derived claims scoped to expressions, bindings, identities, and
   control-flow edges.

## Hard Principles

- **One algebra.** `nil`, atoms, literals, unions, intersections, complement,
  records, arrows, `unknown`, and `never` are one value-set algebra. Nilability
  is not a separate axis; it is `T | nil`.
- **Annotations are obligations, not axioms.** A signature, overload, guard,
  module declaration, declaration file, or checked cast must generate proof
  obligations before it becomes an exported claim.
- **No name magic.** `pcall`, `require`, `setmetatable`, guards, overloads, and
  stdlib behavior must be expressible by declared types plus principled
  primitives. A name-keyed handler is a design smell.
- **Mutation is identity-sensitive.** Lua tables are mutable identities. Shape
  claims over tables must account for construction, writes, aliases, sealing, or
  another explicit identity discipline.
- **Effects are not value types.** If v6 has effects, they live on arrows as
  call/capability obligations. They do not enter the value-set algebra.
- **Demand the decision.** Where local derivation is not cheap, terminating, and
  legible, require an annotation or reject the feature shape.
- **Delete rather than patch.** If a feature needs ad-hoc interactions with many
  existing rules, derive a smaller primitive that explains it or leave the
  feature out.

## Semantic Objects

### Value Claims

The value algebra starts with:

- `nil`
- atoms: `boolean`, `integer`, `number`, `string`, `thread`, `userdata`,
  `cdata`
- literals: singleton strings, booleans, integers, and numbers
- `unknown`: top value claim, usable only where top is explicitly accepted
- `never`: bottom value claim
- union: `A | B`
- intersection: `A & B`
- complement: `~A`
- arrows: parameter pack, return pack, optional effect row
- table identities and record observations
- nominal wrappers: `newtype`, `opaque`, private fields if retained

`any` is not part of the sound value algebra. It is an explicit unsafe boundary.
Every use should be visible, counted, and grep-able.

### Movement Sites

Movement sites are the only places where claims matter:

- binding
- assignment
- function call
- operator application
- return
- table field/index read
- table field/index write
- branch edge
- control-flow join
- annotation/cast
- overload declaration
- guard declaration
- module boundary
- FFI/dynamic boundary

### Facts

Facts are derived, scoped claims. They are not arbitrary annotations copied into
the environment.

Minimum fact kinds:

- expression claim: `expr_id -> Type`
- binding claim: `symbol_id -> Type`
- identity claim: `identity_id -> TableState`
- flow fact: `(edge_id, symbol_id) -> Type`
- module fact: `module_name -> exported Type`
- obligation: `producer Type <: consumer Type` plus source span and reason

Facts must have invalidation rules. In particular, table identity facts and flow
facts can be invalidated by writes, aliasing, and calls that may mutate.

## Type Algebra

### Subtyping

Subtyping is the producer/consumer relation: `A <: B` means every value in `A`
is safe where `B` is required.

Required laws:

- `never <: T`
- `T <: unknown`
- `T <: T`
- `A <: B | C` if `A <: B` or `A <: C`, with a specified union-right rule
- `A | B <: C` if `A <: C` and `B <: C`
- `A <: B & C` if `A <: B` and `A <: C`
- `A & B <: C` if either intersection member is sufficient, or by normalized
  set-algebra reduction
- `A <: ~B` iff `A & B` is empty, subject to bounded emptiness checking
- literals subtype their base atoms
- `integer <: number`

Pinned first implementation: bounded disjunctive-normal normalization with the
budgets specified in "Algebra Normalization" below. A proof that exceeds the
budget rejects with a legible complexity diagnostic.

### `unknown`

`unknown` is top, but it is not a silent producer for concrete consumers. A
value whose only known claim is `unknown` must be narrowed or annotated before
use at a concrete consumer.

This policy avoids using `unknown` as a disguised `any`.

### `any`

`any` is an unsafe boundary, not a fallback.

Rules:

- assigning to/from `any` is permitted;
- every implicit introduction of `any` is a warning or error, depending on the
  boundary;
- no v6 inference rule may choose `any` to recover from failure;
- explicit unsafe casts and dynamic boundaries should be grep-able.

## Proof Obligations

An annotation or declaration does not assert truth. It creates obligations.

Examples:

- `local x --: T = expr` emits `typeof(expr) <: T`, then exports `x: T`.
- `expr --[[: T]]` emits `typeof(expr) <: T`, then treats the expression as `T`.
- A function signature checks the body under the signature.
- An overload checks the body once per overload signature.
- A type guard checks every `true` return path proves the predicate.
- A module declaration checks the exported value against the module type.
- A stdlib declaration is trusted only if it is explicitly classified as a
  boundary; otherwise it is a declaration consumed by normal checking.

## Thin Verticals

Each vertical is a slice through the full semantics. It owns one unavoidable
primitive or movement-site family end-to-end.

A vertical is acceptable only if:

- it has fixtures;
- it adds no name-specific handlers;
- it defines its fact inputs and fact outputs;
- it specifies invalidation if it produces scoped facts;
- it can be disabled without changing the meaning of earlier completed
  verticals, except that later verticals may lose precision or become
  unavailable.

### 1. Value Algebra + Subtyping

Owns value-set claims and `producer <: consumer`.

Scope:

- atoms, literals, `nil`, `unknown`, `never`;
- union, intersection, complement;
- deterministic normalization;
- bounded emptiness;
- display and diagnostics for algebra failures.

Fact inputs:

- none beyond parsed type syntax.

Fact outputs:

- normalized type nodes;
- subtype proof success/failure;
- complexity-limit diagnostics.

Required fixtures:

- literal widening;
- `nil` as ordinary union member;
- union-left and union-right behavior;
- intersection as overload representation but not overload checking;
- complement basics: `string <: ~number`, not `string <: ~string`;
- `unknown` accepted as consumer but rejected as producer for concrete use-site
  checks.

Out of scope:

- callable arrows;
- table field structure;
- generics;
- effects.

### 2. Bindings + Annotations

Owns local bindings, assignments, checked casts, and declaration obligations.

Rules:

- unannotated locals receive the producer claim;
- annotated locals emit a subtype obligation;
- assignment to a mutable binding checks against the binding's current claim or
  updates the claim only in explicitly specified construction contexts;
- checked casts are proof obligations;
- unsafe casts are explicit unsafe boundaries if v6 keeps them.

Fact inputs:

- expression claims from earlier syntax walks;
- subtyping.

Fact outputs:

- binding claims;
- cast result claims;
- obligation diagnostics.

Required fixtures:

- annotation rejects bad producer;
- checked cast rejects bad producer;
- `unknown` cannot satisfy a concrete annotation without proof;
- `any` use is visible.

### 3. Arrows + Calls

Owns function literals, parameters, returns, call-site checking, and operator
application.

Rules:

- an arrow has parameter pack and return pack;
- checking a function against an arrow binds parameters to the declared
  parameter claims and checks every return against the declared return pack;
- calling an arrow checks argument claims against parameter claims and produces
  return claims;
- operators are ordinary declared arrows unless a Lua syntax form forces a
  primitive rule;
- function values without a known arrow cannot be called without annotation or
  narrowing.

Fact inputs:

- binding claims;
- subtyping;
- parsed function bodies.

Fact outputs:

- function expression claims;
- call expression claims;
- return obligations.

Required fixtures:

- function body return mismatch;
- wrong argument type;
- extra/missing argument behavior;
- multi-return baseline, even if rich pack features are deferred;
- operator application through declared arrows.

Out of scope:

- overload body multiplication;
- effects;
- generics beyond monomorphic annotations.

### 4. Overloads

Owns overloaded implementation checking and overloaded call resolution.

Rules:

- overloaded function type may be represented as an intersection of arrows;
- soundness comes from checking the implementation once per overload signature;
- only after every overload body check succeeds does the function export the
  overloaded type;
- call resolution against an overloaded value must be deterministic and
  documented.

Ambiguity policy:

- matching branches return the union of matching returns;
- if effects are later admitted, matching branch effects are joined;
- never silently pick the first declaration.

Fact inputs:

- arrows;
- subtyping;
- function body checker.

Fact outputs:

- exported overloaded claim;
- call result claim for overloaded calls.

Required fixtures:

- implementation satisfies all overloads;
- implementation satisfies one overload but fails another;
- ambiguous call;
- union argument call;
- overload with different return claims.

### 5. Tables as Identity

Owns table construction, field reads, field writes, and table identity.

This is the hard slice. Do not bundle it with metatables.

Core stance:

- a Lua table is a mutable identity;
- a record type is a structured observation of a table identity;
- writes change or check facts about the identity;
- reads consume the current observation.

Pinned model:

- `{}` obtains a fresh identity in an open construction phase;
- direct writes to a fresh unescaped identity extend its record observation;
- assigning the identity to an annotated binding checks/seals against that
  annotation;
- passing the identity to an unknown function, storing it into an unknown table,
  or returning it from the construction scope ends precise construction unless
  annotated;
- writes to a sealed identity are checked against existing mutable fields and
  reject writes to absent or readonly fields;
- exposed aliases invalidate flow-sensitive field facts unless the write target
  is provably disjoint.

This model is intentionally conservative. It prefers demanding annotations at
aliasing boundaries over trying to infer global mutation behavior.

Fact inputs:

- binding claims;
- flow facts for identity freshness;
- subtyping.

Fact outputs:

- identity facts;
- record observations;
- read expression claims;
- write obligations.

Required fixtures:

- `{ x = 1 }` read of `x`;
- assigning new field during construction;
- rejected missing field after seal;
- rejected write through readonly field;
- alias invalidation case;
- annotation sealing case;
- open record width subtyping.

### 6. Flow + Guards

Owns branch narrowing, joins, intrinsic guards, and verified user-defined guards.

Rules:

- branches produce edge facts;
- joins keep only claims valid on all incoming edges;
- narrowing is scoped and invalidated by mutation/aliasing that can falsify the
  narrowed claim;
- intrinsic guards include `x ~= nil`, `type(x) == "string"`, literal equality,
  and discriminant field equality;
- user-defined type guards are not trusted.

Verified guard rule:

```lua
--: (unknown) -> x is Point
local function is_point(x)
  ...
end
```

The signature creates an obligation: every `true` return path must prove `x:
Point`. If the checker cannot prove that locally, the declaration is rejected or
the function is only `(...) -> boolean`.

Fact inputs:

- expression claims;
- table observations;
- control-flow graph;
- subtyping.

Fact outputs:

- edge facts;
- narrowed binding claims;
- verified guard claims.

Required fixtures:

- nil guard;
- `type()` guard;
- tag-field guard;
- invalid user guard rejected;
- valid user guard accepted;
- mutation invalidates a narrowed table field fact.

### 7. Modules + Stdlib Declarations

Owns `require`, module return claims, explicit globals, and stdlib typing.

Rules:

- no ambient globals;
- every global must be local, required, or declared;
- module declarations create obligations for the exported value;
- `require` must be explained by module declarations and a principled primitive
  for literal module lookup if needed;
- stdlib behavior is declarations plus explicit trusted boundaries, not checker
  name magic.

Primitive:

- `Require<"module.name">` is the one type-level lookup primitive for literal
  module names. It reads the module fact table. It is not a general evaluator and
  not a name-keyed handler.

Fact inputs:

- file/module graph;
- module declarations;
- exported expression claims.

Fact outputs:

- module facts;
- imported binding claims;
- undeclared-global diagnostics.

Required fixtures:

- declared module import;
- undeclared module returns `unknown` or errors according to pinned policy;
- module export fails declaration;
- no ambient `io`/`os`;
- stdlib declaration use without handler.

### 8. Metatables + Methods

Owns `setmetatable`, `__index`, metamethod lookup, and `:` dispatch.

Prerequisite:

- table identity is already specified.

Rules:

- `setmetatable` is a table-identity operation that changes future field/method
  observation rules for that identity;
- it is not a name-keyed shortcut;
- `__index` chain walking must terminate and have a visible cycle policy;
- method dispatch is field lookup plus receiver passing.

Pinned model:

- `setmetatable` is permitted only on fresh/open identities;
- it seals the structural observation of the table;
- re-metatable and removing metatable are rejected in v6 core;
- `__index` table chains are walked with visited identity set;
- `__index` function requires an arrow claim and returns the field claim;
- metamethod operator lookup feeds the ordinary arrow/call checker.

Fact inputs:

- table identity facts;
- arrow/call checker;
- field lookup.

Fact outputs:

- metatable observation facts;
- method field claims;
- metamethod operator arrows.

Required fixtures:

- `obj:method(a)` receiver passing;
- table `__index` chain;
- cyclic `__index` terminates;
- `__index` function typed;
- rejected re-metatable.

### 9. Generics

Owns parametric and bounded polymorphism.

Start with:

- ordinary type parameters;
- structural bounds;
- instantiation at call sites;
- generalization only at well-defined let/export boundaries;
- no HKTs until corpus pressure proves need.

Rules:

- generics preserve relationships between producer and consumer claims;
- generic parameters are not implicit `any`;
- bounds are checked by subtyping;
- generic function bodies are checked once under symbolic parameters, not by
  sampling concrete instantiations.

HKTs:

- not core;
- admitted only if a real API must quantify over type constructors;
- require an interaction spec with records, arrows, subtyping, and display before
  implementation.

Fact inputs:

- subtyping;
- arrows;
- annotation declarations.

Fact outputs:

- polymorphic claims;
- instantiated claims.

Required fixtures:

- identity function;
- bounded generic field access;
- rejected bound violation;
- generic table container;
- no `any` leakage from unresolved type parameters.

### 10. Optional Capability Effects

Owns capability/effect claims on arrows, if admitted.

Effects are not value sets. They are obligations attached to calls.

Rules:

- an arrow may carry an effect row;
- calling the arrow emits the effect obligation;
- a function body must not perform effects outside its declared row;
- overloaded branches may carry distinct effect rows;
- call-site effect computation follows overload resolution.

Admission test:

- if capability discipline can be enforced by ordinary value/module claims,
  skip effects;
- if platform capability safety requires knowing which calls may perform which
  capabilities, admit narrow capability effects on arrows only.

Out of scope:

- arbitrary algebraic effects;
- effect values;
- refinement-style effect predicates.

Required fixtures if admitted:

- pure function rejects `io` call;
- function with `!io` permits `io` call;
- callback effect propagation;
- overload branch with distinct effects.

## Movement Matrix

The v6 spec is pinned only when every completed value form has behavior for
every completed movement site.

| Movement site | Required question |
| --- | --- |
| bind | Does producer claim satisfy the binding annotation or inferred target? |
| assign | Does producer claim satisfy the mutable target, and does mutation change identity facts? |
| call | Does callee have an arrow accepting the argument claims, and what return/effect claims result? |
| operator | Which declared/metatable arrow is consumed, and are operands accepted? |
| return | Does returned producer claim satisfy the function's promised return claim? |
| index/read | Does the receiver claim support this key, and what value claim is produced? |
| field write | Does the receiver identity allow this update, and what claim changes? |
| branch | Which facts become true on each edge? |
| join | Which claims survive all incoming edges? |
| annotation/cast | What proof obligation is generated? |
| overload declaration | Does the implementation satisfy every branch? |
| guard declaration | Do all true paths prove the predicate? |
| module boundary | Which claims are exported/imported, and which obligations must be proven? |
| dynamic boundary | Is the unsafe claim visible and contained? |

## Pinned Policy Choices

These choices are pinned for v6 core unless implementation fixtures disprove
them.

### Overload Ambiguity

If a call matches multiple overload branches, the result claim is a union of
whole matching branch return packs, as specified by
`docs/typechecker-v6-kernel-synthesis.md`'s `PackResult` domain. It is not a
slotwise union of return positions. The effect claim is the join of all matching
branch effects if effects are enabled.

Reason: this is deterministic, sound, and avoids an arbitrary first-match rule.
If the union result is too imprecise for the caller, the caller narrows or
annotates.

### Undeclared Modules

An undeclared literal `require("x")` is an error in strict v6 mode. A dynamic
`require(expr)` where `expr` is not a known literal is an explicit `unknown`
boundary unless a manifest/module declaration supplies a stronger claim.

Reason: no ambient module graph and no silent widening.

### Unsafe Boundaries

v6 keeps one explicit unsafe cast spelling, `--[[:! T]]`, only as a grep-able
boundary. The checked cast remains `--[[: T]]`.

Rules:

- checked cast: proves `typeof(expr) <: T`;
- force cast: emits an unsafe-boundary diagnostic or audit event, then exports
  `T`;
- no inference rule may synthesize a force cast.

### Table Identity

v6 core uses open/sealed table identity phases.

Rules:

- table literals create a fresh open identity;
- direct writes to a fresh unescaped open identity extend its observation;
- assigning to an annotated binding, returning from the construction scope,
  passing to a call with unknown mutation behavior, or storing into an unknown
  container seals or escapes the identity;
- sealed identities reject absent-field writes and readonly writes;
- exposed aliases invalidate flow-sensitive field facts unless the write target
  is provably disjoint.

This is conservative by design. It can reject valid Lua patterns; rejected
patterns become annotation obligations or later explicit mechanisms.

### `Require<literal>`

v6 admits one module lookup primitive: `Require<"module.name">`.

It is a lookup into the module fact table, not a general evaluator and not a
name-keyed handler. It is valid only for literal module names. Dynamic require
uses the undeclared/dynamic module policy above.

### Effects

Effects are not part of v6 core. They are a reserved extension point on arrows.
No core vertical may depend on effects. If admitted later, they must satisfy the
Optional Capability Effects vertical.

### HKTs

HKTs are not part of v6 core. Ordinary and bounded generics are core. HKTs
require a corpus-driven admission document.

## Normative Core Spec

This section is intentionally closer to implementation than philosophy. Names
are descriptive; exact Lua module names can differ, but the semantics should not.

### Type AST

The core type representation must distinguish these node kinds directly:

```lua
Type =
  | { tag = "atom", name = "nil" | "boolean" | "integer" | "number" |
                         "string" | "thread" | "userdata" | "cdata" }
  | { tag = "literal", base = AtomName, value = unknown }
  | { tag = "unknown" }
  | { tag = "never" }
  | { tag = "any" }
  | { tag = "union", members = { Type } }
  | { tag = "intersection", members = { Type } }
  | { tag = "complement", of = Type }
  | { tag = "arrow", params = Pack, returns = Pack, effects = EffectRow | nil }
  | { tag = "record", fields = { [string] = Field }, indexes = { Index },
      row = RowState }
  | { tag = "nominal", kind = "newtype" | "opaque", name = string,
      body = Type }
  | { tag = "var", id = integer, bound = Type | nil }
```

Core v6 should not encode structural facts in strings. No `$opt_x`, `$idx_1`,
`$Lit`, or equivalent name prefixes.

`any` is represented so boundaries can be tracked, but it is excluded from
normal soundness proofs.

### Packs

Function parameters, returns, and multi-return use `Pack`:

```lua
Pack = { items = { Type }, rest = Type | nil }
```

Rules:

- no more than one `rest`;
- fixed arity when `rest == nil`;
- extra returned values may be discarded by Lua assignment/call context only at
  the movement site that performs the discard;
- missing returned values become `nil` only where Lua semantics actually pad.

### Records

Records are observations of table identities and also appear as structural
requirements.

```lua
Field = { type = Type, optional = boolean, readonly = boolean }
Index = { key = Type, value = Type, readonly = boolean }
RowState = "closed" | "open"
```

Rules:

- named fields shadow indexers for literal field lookup;
- optional means the field may be absent, not that the field is always present
  with `T | nil`;
- reading an absent optional field produces `nil`;
- reading an optional field of type `T` produces `T | nil`;
- readonly fields are covariant under subtyping;
- mutable fields are invariant under subtyping;
- width subtyping permits extra fields only when the consumer record is open or
  the extra fields are not observed by the consumer movement site;
- indexer key types are contravariant and value types follow readonly/mutable
  variance.

### Algebra Normalization

v6 uses bounded disjunctive-normal normalization for set operations.

Definitions:

- a **term** is an intersection of positive atoms/literals/records/arrows/nominals
  plus negative complements;
- a union is a set of terms;
- normalization distributes intersection over union until a configured term
  budget is reached;
- complements are pushed inward by De Morgan rules where doing so stays within
  budget.

Required implementation limits:

- term budget default: 256;
- recursion depth budget default: 64;
- if a proof exceeds budget, emit `TYPE_COMPLEXITY_LIMIT` with the operation and
  source span;
- complexity-limit failure is a rejection, not acceptance.

This gives a terminating first implementation. Budgets can be tuned later, but
no implementation may silently widen to `unknown` or `any` when the budget is
exceeded.

### Subtyping Algorithm

`is_subtype(A, B)`:

1. Normalize aliases and nominal transparency according to visibility.
2. If `A` is `never`, accept.
3. If `B` is `unknown`, accept.
4. If `A` is `unknown` and `B` is not `unknown`, reject unless the movement site
   explicitly accepts unknown.
5. If either side is `any`, route through unsafe-boundary handling, not normal
   proof.
6. Normalize unions/intersections/complements within budget.
7. Apply literal widening and atomic lattice edges.
8. Apply arrow subtyping: params contravariant, returns covariant, effects
   subset if effects are enabled.
9. Apply record subtyping with field/index variance.
10. Apply nominal rules.
11. Otherwise reject with the first meaningful mismatch.

The implementation may use memoization and structural hashes, but observable
behavior follows this order.

### Expression Checking

Each expression check returns:

```lua
ExprResult = {
  type = Type,
  facts = { Fact },
  obligations = { Obligation },
}
```

Expression rules:

- literals produce literal claims;
- `nil` produces atom `nil`;
- variable references read the current binding claim plus active flow facts;
- table literals create fresh table identities and record observations;
- function literals produce arrows only when parameter/return claims are known
  or inferred by a completed vertical;
- calls consume arrow claims;
- field/index reads consume table/record observations;
- casts produce obligations or unsafe-boundary events.

### Statement Checking

Each statement check transforms an environment:

```lua
Env = {
  bindings = { [symbol_id] = Type },
  identities = { [identity_id] = TableState },
  flow = { FlowFact },
  modules = { [module_name] = Type },
}
```

Statement rules:

- local declaration adds a binding claim after obligations pass;
- assignment checks or updates the target according to target kind;
- return checks against the current function return pack;
- if-statements produce branch edge facts and join them after branch checking;
- function declarations are local declarations whose producer is an arrow or
  overload claim;
- module return checks against module declaration if one exists.

### Diagnostics

Diagnostics are part of the spec. Every rejection must name:

- producer claim;
- consumer requirement;
- movement site;
- source span;
- reason code.

Core reason codes:

- `TYPE_MISMATCH`
- `UNKNOWN_REQUIRES_NARROWING`
- `UNSAFE_ANY_BOUNDARY`
- `ANNOTATION_UNPROVEN`
- `OVERLOAD_BRANCH_UNPROVEN`
- `OVERLOAD_NO_MATCH`
- `TABLE_FIELD_MISSING`
- `TABLE_WRITE_REJECTED`
- `READONLY_FIELD_WRITE`
- `GUARD_UNPROVEN`
- `MODULE_UNDECLARED`
- `TYPE_COMPLEXITY_LIMIT`
- `NAME_MAGIC_REJECTED`

## Feature Admission Rules

### Overloads

Have them. They are required for ordinary Lua/stdlib APIs and can be sound if
implemented obligation-first.

Core rule:

- representation may be intersection of arrows;
- implementation proof is checking the body under every overload signature.

### Type Guards

Have them only if verified.

Core rule:

- a guard signature is a proof obligation;
- if the body cannot prove the predicate on true paths, reject the guard or
  downgrade to boolean.

### Refinement Types

Do not have full refinements.

Use instead:

- literals;
- union/intersection/complement;
- flow narrowing;
- verified guards;
- opaque/newtype constructors for validated values.

Reason:

- arbitrary predicates turn the checker into a theorem prover and undermine the
  terminating/legible floor.

### HKTs

Defer.

Admit only after a real corpus API requires quantifying over type constructors
and the interaction matrix remains legible.

### Effects

Reserved extension, narrowly.

Admit only as arrow capability obligations if platform capability safety needs
them. Do not model effects as value types.

## v5 Mining Policy

v5 should be mined for discoveries, not repaired in place.

Import candidates:

- set-theoretic algebra lessons;
- literal/record/pack representation lessons;
- parity and operational-semantics fixtures;
- known failure cases and soundness bugs;
- good diagnostics or tests.

Do not import:

- name-keyed handlers;
- accidental solver dispatch order unless re-derived as a formal rule;
- `$`-encoded structural facts;
- feature scaffolding that has no live path;
- implementation choices that only exist because v5 was built in the wrong
  order.

## Implementation Strategy

Build v6 beside v4. Do not replace v4 until v6 proves better on pinned fixtures
and selected corpus files.

For each vertical:

1. Write the semantic rule and movement-matrix cells.
2. Add fixtures for accept/reject and edge cases.
3. Implement the smallest engine slice.
4. Run v6 fixtures.
5. Compare selected corpus files against v4 for diagnostic quality and
   regression risk.
6. Only then let later verticals consume its facts.

No vertical may land with TODO-shaped behavior in a completed cell. A deferred
cell must reject with a legible diagnostic or demand an annotation.

## Proposed Module Layout

Exact names can change, but v6 should keep these responsibilities separate:

```text
lib/type/static-v6/
  init.lua              public API
  ast.lua               thin adapter over existing parser AST
  types.lua             Type/Pack/Record constructors + structural hashing
  normalize.lua         union/intersection/complement normalization
  subtype.lua           producer <: consumer
  env.lua               bindings, identities, modules, flow facts
  obligations.lua       obligation representation + checking dispatcher
  expr.lua              expression checking
  stmt.lua              statement/block checking
  arrows.lua            function/call/operator rules
  overloads.lua         overload declaration + call resolution
  tables.lua            table identity + record observations
  flow.lua              branch facts + joins
  guards.lua            intrinsic and verified user guard rules
  modules.lua           require/module/stdlib declaration rules
  metatables.lua        setmetatable/__index/method dispatch
  generics.lua          parametric/bounded generics
  effects.lua           reserved; absent from core until admitted
  diagnostics.lua       reason codes + formatting
  cli.lua               optional CLI entry point
```

Dependency direction:

- `types` has no dependency on checker passes.
- `normalize` depends only on `types`.
- `subtype` depends on `types` and `normalize`.
- `expr`/`stmt` depend on `env`, `subtype`, and admitted vertical modules.
- feature modules may depend on earlier verticals, never on later verticals.
- no module may special-case a stdlib name to change semantics.

## Corpus Gates

Do not run v6 across the full repo as an early success metric. Use pinned corpus
files per vertical:

- algebra/bindings/arrows: small synthetic files only;
- tables: simple table-heavy libraries with few metatables;
- flow/guards: files with discriminated unions and `type()` checks;
- modules: small libraries with explicit module return tables;
- metatables: focused object/prototype-style libraries;
- generics: `lib/fp/*` only after ordinary generics are stable.

For each corpus gate, compare:

- number of diagnostics;
- first five diagnostics by source order;
- whether each diagnostic is a real bug, annotation obligation, or v6 missing
  feature;
- whether v6 avoided v4/v5 known false positives.

Corpus gates are advisory until the vertical's conformance fixtures pass.

## Open Questions

- Are capability effects necessary once modules and explicit caps are modeled as
  values? Effects are reserved but not core.
- Which concrete corpus files should be the first table-identity gate?
- Does `setmetatable` sealing reject too much real crescent code? If yes, design
  a smaller explicit mechanism rather than loosening by name.
- Should force casts be errors outside files/modules explicitly marked as
  boundary code?
- What exact annotation syntax represents verified type guards in v6 if current
  syntax is insufficient?

## Done Definition

v6 is worth implementing only if this remains true throughout:

- Every admitted feature is explained by value sets plus movement sites.
- Every annotation creates a proof obligation or an explicit unsafe boundary.
- Every overload and type guard is producer-checked before it becomes an exported
  claim.
- Table mutation and aliasing have an explicit identity discipline.
- No completed vertical requires a name-specific handler.
- Every interaction is covered by fixtures before the next vertical depends on
  it.
- v5 mechanisms are imported only after re-derivation, never because they already
  exist.
